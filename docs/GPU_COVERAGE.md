# GPU coverage of the ghidra-mcp tool catalog

Generated by `python -m tools.gpu.coverage --write` from `tests/endpoints.json` and
`GpuService.TOOL_MAP`; `tests/unit/test_gpu_coverage.py` fails if a tool is unclassified.

**209 upstream tools: 37 have a GPU twin, 172 have no computation to port.**
Every GPU twin also runs on the CPU (`backend=cpu`), so nothing was lost by porting.

## Code review: every program-wide loop outside the GPU tools

Every place a non-GPU tool (or a helper it calls) iterates a whole-program collection was read in context. Verdicts:

| Tool / helper | Verdict |
| --- | --- |
| `rename_function` | ported: token-subset collision check against every function name -> gpu_name_collisions (batched; CPU twin matches NamingConventions.findTokenSubsetCollision exactly) |
| `analyze_function_completeness` | ported: its name-collision check over all function names -> gpu_name_collisions; the rest is per-function decompiler-driven scoring |
| `find_data_types` | ported: substring over every data type name and path -> gpu_find_functions scope=data_types |
| `list_class_members` | ported: namespace / implicit-this filter over every function -> gpu_find_functions scope=class_members |
| `archive_ingest_program` | partly ported: the per-function opcode SHA-256 -> gpu_function_hashes kind=opcode; the rest builds upload payloads from DB reads |
| `batch_string_anchor_report` | string extraction is gpu_list_strings; the report itself joins defined strings to their referencing functions through DB indexes (no arithmetic) |
| `get_entry_points` | walks all symbols keeping isExternalEntryPoint -- a stored flag, so the cost is the walk itself |
| `list_program_items` | enumerates one kind of item and pages it (collectMethodNames/ClassNames/Exports/Namespaces); no predicate to compute |
| `list_bookmarks` | enumerates bookmarks and pages them |
| `merge_program_documentation` | copies every documented item to the same address in another program: address-keyed DB lookups and writes, nothing data-parallel |
| `disassemble_function` | getFunctions(start, true) only to find the next function boundary (bounded) |
| `analyze_for_documentation` | reference iteration bounded to one function body (getReferenceSourceIterator(body)) |
| `create_label` | symbol iterator at one address |
| `set_global` | findEvictionVictims: symbols in the range being retyped (bounded) |
| `resolve_duplicate_type` | findAllTypesBySimpleName: one name looked up across data types |
| `(name lookups)` | ServiceUtils.functionsNamedIgnoreCase / searchByNameInAllCategories: one name resolved per call, a single equality pass -- cheaper than a host-to-device copy of the names |
| `(struct matching)` | AnalysisService.findMatchingStructType: a few parameter names matched against data type names inside per-function completeness/documentation analysis |

Every other non-ported tool touches a bounded number of records per call (one address, one function, one type, one setting) or is lifecycle/I-O.


## Not ported: nothing a GPU could compute

These tools are database edits, single-record lookups, I/O, lifecycle or UI actions, or
wrap Ghidra's native decompiler / SLEIGH disassembler. Moving them to a GPU would only add
a host-to-device copy around a lookup.

### What was measured

`python -m tools.gpu.measure_cpu_only` called these tools on kernel32.dll (Windows 11, x64, 4301 functions incl. externals, auto-analysed) (best of 3, wall time including HTTP; write tools as `dry_run=true`, i.e. inside a transaction that is rolled back).

- **172 of 172 timed** (109 read-only, 63 writes). Median **15.5 ms**. A no-op request (`/check_connection`) took between 0.5 and 15.6 ms across the measurement runs (Windows loopback HTTP), so the many 1-20 ms rows are mostly request overhead around a lookup or a single transaction.
- Every timed tool slower than 100 ms, and where its time goes (each has its own reason in the table):
  - `set_image_base` 26277 ms
  - `debugger/launch` 6786 ms
  - `run_ghidra_script` 3230 ms
  - `archive_project` 2052 ms
  - `analyze_struct_field_usage` 1457 ms
  - `get_functions` 965 ms
  - `restore_project` 870 ms
  - `import_file` 864 ms
  - `export_program` 724 ms
  - `analyze_for_documentation` 711 ms
  - `run_script_inline` 647 ms
  - `batch_set_comments` 519 ms
  - `set_variable_type` 466 ms
  - `archive_ingest_program` 421 ms

  - `get_function_pcode` 375 ms

- **Every one of them was timed.**

How the hard ones were reached: GUI-only tools in a real Ghidra GUI started with an isolated settings directory (`-Dapplication.settingsdir`, no access to the user's projects); debugger tools against a live dbgeng trace of a launched `whoami.exe`; Ghidra Server tools against a scratch server bound to 127.0.0.1 (`python -m tools.gpu.measure_live`); tools that refuse a dry run (save, export, import, archive, project lifecycle, scripts, analysis) for real on a throwaway project.
